# Version 0.3: design note

Status: draft for review, 8 November 2026. Not released; the code says 0.3.0.dev0.

## What 0.3 adds

Version 0.2.0 gives one of two answers, `match` or `no_match`, and takes array letters as written on
the record's strand. Version 0.3 stops assuming the strand. For single-letter records (SNVs) it
recognises three situations that 0.2.0 either got wrong or folded into `no_match`:

- letters that fit the record only on the other strand (a strand flip);
- A/T and C/G sites, whose two letters are the same pair on both strands, where the strand decides
  the answer;
- data rows that give the record's reference and alternate the other way round (a swap).

It also adds a VCF mode, so the variants a pipeline may report (a records VCF) can be checked
against a person's VCF first, and a draft WDL workflow around that mode.

## Outcomes

| Outcome | Meaning | What a pipeline should do |
|---|---|---|
| `match` | The data confirms the record as written. | It may report the record. |
| `match_after_flip` | The letters fit the record only when complemented (A with T, C with G), and complemented they hold the record's alternate allele: the data and the record are written on opposite strands, or one of them is wrong. Complemented letters that hold only the reference are `no_match`, and only the reason names the flip. | Count it only if the pipeline corrects strand on purpose, for example from the array manifest, and then as its own outcome. Never report it as a plain match. |
| `ambiguous_strand` | An A/T or C/G site where the letters cannot show the strand and it could change the answer: a homozygous array call, or a data row that gives the record's two letters the other way round, whatever its genotype, because a row whose reference disagrees is never a match. | Do not report it from these letters. The array manifest's strand, or the data provider's stated strand, could resolve it. Allele frequencies cannot for one person: they can only suggest a strand for many people typed on the same array, and tools treat even that as unreliable. This kit uses neither. |
| `ref_alt_swapped` | A data row gives the record's reference as its alternate and the record's alternate as its reference, as written or after complementing. At an A/T or C/G site such a row is `ambiguous_strand`. Two descriptions that both give the genome's reference base at a position cannot disagree about it. | Do not report it. Check the genome build and the allele order of both files. |
| `no_match` | The data does not confirm the record. Unchanged from 0.2.0. | Do not report it. It is not a negative result for the person. |
| `no_genotype` | VCF mode only: the data has no usable two-allele genotype at the record's position. | Do not report it. A missing row is not a reference call. |

A yes/no matcher (the 0.2.0 interface) passes a case when it answers yes exactly for `match`. Every
other outcome expects no, so a pipeline that never reports anything uncertain still passes. A matcher
that returns outcome names is scored on the exact name.

## The reference rule

In both paths, a record or a held allele with a letter other than A, C, G and T, such as N, is
`no_match` first: such letters confirm nothing.

**Array letters** (no reference or alternate of their own):

1. The record must be a single-letter change; otherwise `no_match`, as in 0.2.0.
2. A/T or C/G record: a heterozygous call is `match`, because it holds one copy of the alternate
   allele on either strand. A homozygous call is `ambiguous_strand`: T/T against `A>T` is two copies
   of T on the record's strand and none on the other. Any other letter is `no_match`.
3. Any other single-letter record: letters that fit as written give `match` or `no_match` as in 0.2.0.
   Letters that fit only when complemented give `match_after_flip`, or `no_match` if the complemented
   letters hold only the reference. Letters that fit neither reading give `no_match`.

**Data rows** (imputed or sequenced, with their own reference and alternate):

1. If the reference bases agree with the record's, the row is compared as in 0.2.0, by minimal
   representation. A row with several alternate alleles matches when one of them is the record's
   variant and the genotype holds it.
2. If the reference disagrees and the record is a single-letter change:
   - an A/T or C/G record whose alleles the row gives the other way round is `ambiguous_strand`,
     whatever its genotype: the row may be on the other strand or may be swapped, for a homozygote the
     two readings give opposite answers, and a row whose reference disagrees is never a match;
   - a row that, complemented, equals the record is `match_after_flip`, or `no_match` if the
     complemented genotype holds no alternate allele;
   - a row with the record's alleles the other way round is `ref_alt_swapped`;
   - a row that, complemented, has the record's alleles the other way round is also `ref_alt_swapped`.
3. Any other reference disagreement is `no_match`, as in 0.2.0.

Assumptions, stated in the README too:

- A data row whose reference agrees with the record is taken at face value, even at an A/T or C/G
  site, as the VCF specification expects (REF is the reference genome's base at POS). A row on the
  other strand with its alleles also swapped would read the same. In VCFs made from array data
  without checking REF against a genome that is one slip, not two (PLINK writes its A2 allele as
  REF, flagged `PR`), so the README asks for `bcftools +fixref` on such files first.
- Strand reasoning assumes the site has no alleles beyond the record's two. Letters that fit only on
  the other strand could, at a site with more alleles, be two other alleles on the record's strand.
- Flips and swaps are recognised for single-letter records only. An indel on the other strand sits
  at a different position and needs a reference genome. An insertion and a deletion at one position
  can be two real, different variants, so they are never called a swap.

## The eight new cases

| Case | Record | Data | Outcome | Why it is there |
|---|---|---|---|---|
| `array-strand-flip` | `A>G` | array `T/C` | `match_after_flip` | Complemented, `T/C` reads `A/G`. A rule that complements silently reports it as a match. |
| `imputed-strand-flip` | `A>G` | row `T>C`, `C/C` | `match_after_flip` | The same flip in a VCF row. |
| `array-palindromic-homozygous` | `A>T` | array `T/T` | `ambiguous_strand` | Two copies or none, depending on strand. 0.2.0 called this a match. |
| `array-palindromic-homozygous-reference` | `C>G` | array `C/C` | `ambiguous_strand` | A rule that tries the complement whenever the letters as written are not a match turns this into a homozygous match. |
| `array-palindromic-heterozygous` | `G>C` | array `G/C` | `match` | One copy on either strand. Guards against flagging every A/T or C/G site. |
| `imputed-ref-alt-swapped` | `A>G` | row `G>A`, `G/G` | `ref_alt_swapped` | Two copies of the record's alternate by letter, homozygous reference by the row's own labels. |
| `imputed-palindromic-reference-disagrees` | `A>T` | row `T>A`, `T/T` | `ambiguous_strand` | Swap or flip cannot be told apart, and they give opposite answers. |
| `imputed-palindromic-row-agrees` | `C>G` | row `C>G`, `G/G` | `match` | An agreeing reference is taken as the forward strand, so the same letters as an ambiguous array call are a match here. |

All coordinates and letters are invented. The twelve 0.2.0 cases keep their expectations.

## Known-bad rules

Every case whose outcome is not `match` is failed by at least one known-bad rule, as in 0.2.0.

- `as-written` (new) is the 0.2.0 reference rule. It fails only `array-palindromic-homozygous`, the
  one case whose answer 0.3 changes for a yes/no matcher.
- `auto-flip` (new) complements every letter whenever the letters as written are not a match, and
  tries again. It fails both flip cases and both homozygous A/T, C/G array cases.
- `allele-set` (new) treats a row's reference and alternate as an unordered pair. It fails
  `imputed-ref-alt-swapped` and `imputed-palindromic-reference-disagrees`.
- `string-equal` and `trim-only` now build on the 0.3 reference rule, so each still shows exactly
  one mistake and fails the same single case as in 0.2.0.
- `position-only` and `any-non-reference` are unchanged and fail some of the new cases too.

## What changes for existing users

- Two answers change. A homozygous call at an A/T or C/G array site (`T/T` against `A>T`) was a match
  as written and is now `ambiguous_strand`; the 0.2.0 README listed this as a limit. A record or a
  held allele with a letter other than A, C, G and T (`A>N` against `A/N`, or against a data row
  `A>N`) was a match and is now `no_match`, because such letters confirm nothing. No existing case
  changes its expectation.
- `cases.json` `expect` can now take five values. Readers that test `expect == "match"` keep working;
  readers that assume only two values must be updated.
- `run_cases` and `check --adapter` accept a bool (as before), an outcome name, or an
  `(outcome, reason)` pair such as the kit's own `reference_outcome`. A tuple is read by its first
  element. A name that is not an outcome raises `UnknownOutcome`, and `check` exits with 2.

## VCF mode

```bash
genotype-checks vcf --records records.vcf.gz --data person.vcf.gz [--sample NAME] [--out outcomes.tsv]
```

Inputs:

- `--records`: a VCF, plain or gzip/BGZF, with at least CHROM, POS, ID, REF and ALT. Sample columns
  are ignored. Each alternate allele of a multi-allelic record is checked as its own record.
- `--data`: a VCF, plain or gzip/BGZF, with a GT field. If it has more than one sample, `--sample` is
  required, so the kit never picks a person silently.

Output: a TSV with columns `chrom pos id ref alt outcome genotype reason`, one row per record and
alternate allele, in the order of the records file. `genotype` is the data's alleles as letters
(`.` when there is none). A one-line count of outcomes goes to standard error. The output contains
genotypes from the data file, so it is as sensitive as that file. The exit code is 0 when the check
ran, whatever the outcomes, and 2 when it is called wrongly or cannot read its input (a BCF file is
refused with a hint to convert it) or write its output.

How records meet data rows:

- Same chromosome (a leading `chr` is ignored on both sides, and M and MT are the same chromosome)
  and same position. Only data rows that start at the record's position are compared.
- Multi-allelic data rows are read as written: each GT index picks its allele.
- If several data rows start at one position, each is compared. When two or more of them describe the
  record's variant (its two alleles, as written or complemented) and their outcomes differ, the record
  is `no_match`, and the reason lists each row's outcome; a row without a usable call counts as
  disagreeing. Rows about other variants at the position (split multi-allelic rows, an SNV beside an
  indel) do not count against it: the most confirming outcome is kept, and the reason names the
  others.
- Missing calls (`./.`), half calls (`./1`) and one-allele calls give `no_genotype`, with the reason.
  An ALT of `.` means the row has no alternate allele.
- Records with a symbolic or breakend alternate (`<DEL>`, `*`, `]1:100]A`) or an ALT of `.` give
  `no_match` with that reason: the kit compares letters only. So do records with a letter other than
  A, C, G and T, such as N, even where the data has no row: such letters confirm nothing.

Not done: a genome-build check, left-alignment, rows that start before the record's position (for
example a deletion spanning it), and index-based reading. The whole data file is read, which is slow
for large multi-sample files; the workflow cuts the data down with bcftools first.

## Workflow (draft)

- `workflows/genotype_checks.wdl` (WDL 1.0) has three tasks. `subset_vcf`, scattered over the data
  files and their indexes, keeps the records' positions and the sample with
  `bcftools view -R -s -Oz`. Its regions file spells each record's chromosome with and without `chr`
  (and M as MT), because bcftools matches chromosome names exactly and the kit does not.
  `concat_vcfs` joins the pieces with `bcftools concat`. Both use the BioContainers bcftools 1.23.1
  image, pinned by digest. `check_vcf` runs the VCF mode in the kit's own image and writes the stated
  genome build into the summary.
- `genome_build` is a required input. The kit matches chromosome and position only, so the records
  and the data must be on the same build; the value is recorded, not checked.
- The kit's image: the `Dockerfile` installs the kit from the repository on `python:3.12-slim`, pinned
  by digest, and `.github/workflows/image.yml` builds it and pushes it to
  `ghcr.io/birinets/genotype-pipeline-checks:<version>` on release tags only, after checking that the
  tag matches the version in the code. Nothing is installed while the workflow runs. The WDL's default
  names the `0.3.0` tag until the image exists; then the digest replaces it.
- `.dockstore.yml` describes the WDL for Dockstore's GitHub App. It sets no `publish` key, which
  Dockstore's documentation says leaves the publish state unchanged; automatic DOIs are off, because
  a DOI cannot be withdrawn; its filter admits release tags only; and `workflows/test.json` gives
  synthetic test inputs from `workflows/test-data/` (written by `synth`, then `bgzip` and `tabix`) as
  raw GitHub URLs under the v0.3.0 tag, which resolve only once that tag exists.
- CI checks the WDL with `miniwdl check` and with `womtool validate` against the test inputs.
- Tried locally with bcftools 1.23.1: the three command blocks, with their placeholders filled in by
  hand, on synthetic files split by chromosome, with records named `1` and `2`, data named `chr1` and
  `chr2`, and one `.tbi` and one `.csi` index. The outcomes equal those of the check on the whole file.
- Not done: a run on a workflow engine, building the image, the CI job, registration on Dockstore, and
  a run on AnVIL with the open 1000 Genomes data. Workflow tests use public or synthetic data only.

## Open questions

1. **Heterozygous calls at A/T and C/G array sites.** The draft says `match` (one copy on either
   strand). The stricter alternative, common in polygenic-score quality control, is
   `ambiguous_strand` for every genotype at such sites. Changing it means editing one case
   (`array-palindromic-heterozygous`) and one branch of the rule.
2. **Face value for agreeing data rows at A/T and C/G sites** (`imputed-palindromic-row-agrees`).
   The alternative is to call every A/T or C/G data row `ambiguous_strand` too.
3. **Outcome names**: `match_after_flip`, `ambiguous_strand`, `ref_alt_swapped`, `no_genotype`.
   They become part of the case-file contract once released.
4. **Case-file contract.** `expect` gains three values. Drafted: `cases.json` carries
   `"schema_version": 2`, separate from the package version; the 0.2.0 file has none, which counts
   as 1. Open: whether the loader should refuse a schema version it does not know.
5. **A multi-allelic case in `cases.json`.** It needs `row_alt` as a list, another contract change.
   For now multi-allelic rows are tested only in VCF mode.
6. **A duplicate row without a call.** In the VCF check, a row without a usable call counts as
   disagreeing with a called row for the same variant, so the record is `no_match`. The alternative
   is to leave such rows out when looking for disagreement, so that the called row decides.
7. **Images.** Drafted: the kit's own image on GHCR, built from the repository on release tags
   (reproducible, no network while the workflow runs, one more thing to maintain), and the
   BioContainers bcftools image. Open: the GHCR package is private until its visibility is changed,
   and workflow engines need it public; and whether to publish to PyPI as well (name to check).
8. **Checking the WDL.** It has not been run or syntax-checked yet (miniwdl or womtool would do it);
   the CI job that runs both has not run either.
9. **Dockstore.** When to install the GitHub App and register, and the publish state. Drafted:
   release tags only, automatic DOIs off, and test inputs that resolve once v0.3.0 is pushed.
10. **The AnVIL test.** Which 1000 Genomes release and build, which sample, and which records VCF (it
    must be public and its licence must allow use).
11. **Scoring strand-corrected reports.** `compare --reported` scores reported records as matches, so
    a pipeline that reports strand-corrected records on purpose fails the flip cases. A second list
    for those could be added.
12. **Release mechanics.** Version 0.3.0 in `pyproject.toml`, `__init__.py` and `cases.json`; tags on
    both remotes; the image digest in the WDL. CI now includes Python 3.14.
13. **Licence classifier.** Whether to keep PyPI's standard OSI licence classifier.
